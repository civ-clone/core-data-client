# core-data-client

How a game talks to a client that isn't in the same process: a game running in a web worker and the page that shows it, say. It knows nothing about which channels there are or what crosses them; the game that uses it names those.

- **`Transport`**: the contract both ends keep. Named channels, each with what is sent on it and what is received (`TransportData`, collected in a `TransportDataMap`), `send` and `receive` on them, and `request` and `reply` for a question and its answer.
- **`Request`**: a question asked on a channel, with its arguments and, as types, what it is answered with (`RequestArgs`, `RequestReturn`).
- **`AbstractTransport`**: the part of a transport that doesn't depend on how messages travel. Each request gets an id of its own, which its reply echoes, so any number can wait on one channel and each gets its own answer, in any order. A `requestFailed` with a request's id rejects it with a `RequestFailed`. When the other side has said nothing for the silence timeout (`defaultSilenceTimeout`, or the `silenceTimeout` it is given) while requests wait, `notAnswering` is called, once for each silence; the silence is timed from the first request, whether or not the other side has spoken yet (one that hasn't is given `startingSilenceFactor` times as long, as it may still be loading), and `silenceTimeout: null` never times it, for a side that waits on a person. `request` resolves with what the request says it returns, and a request carries one argument at most. `dispose()` rejects what still waits, stops the timing and removes the reply listeners; a subclass that learns the other side has gone calls `failAll`. A subclass says how messages are posted (`post`) and heard (`receive`, calling `heard()`).
- **`DataQueue`**: the changes to a game's `DataObject`s queued for the other side, sent as `DataPatch`es in the order they were queued. A value can be a function, built when the queue is sent; one that comes back `undefined`, or throws, is left out and the rest are sent. `take()` empties the queue and then builds what was in it, so a patch queued while the values are built (by one of those functions) stays queued for the next send; `transferData()` and then `clear()` is the older form of the same, which loses such a patch. Nothing is merged: two updates to the same object are two patches, so a caller that wants each object sent once per send queues it once (civ.one's game keeps a set of what it has queued since the last send, and queues each unit, city and square in it once).
- **`DataPatch`**: each change, by the id of the object it changes: `add` or `update`, the value (an `ObjectMap`), and `index`, where in the object the value goes. `null` is the whole object; anything else is a key path into the object as the receiving side holds it, keys separated by `.` and list positions in brackets (`tiles[12]`, `research.complete`). The queue only carries `index`: applying a patch is the receiving side's job (civ.one's is `applyDataPatches` in its client package).
- **`reconstituteData`**: rebuilds a `DataObject`'s `ObjectMap` (from `@civ-clone/core-data-object`) on the other side, with every reference to an object the same object again, cycles included.

civ.one's web renderer (civ-clone/web-renderer) is built on it: its worker and page each extend `AbstractTransport` over `postMessage`, and name their channels in a `TransportDataMap` of their own.
